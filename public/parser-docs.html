01 Gmail Ingestion, Pagination & Pipeline Metrics

Email ingestion runs in fetchAndParse.js via the official Google Gmail REST API (v1). Rather than querying all mail or truncating results at 50 messages, it executes an allowlist query with complete nextPageToken pagination:

fetchAndParse.js — Paginated Allowlist Fetch JavaScript 
const BANK_SENDERS = [
  'transactionalert@indusind.com',
  'onlinesbicard@sbicard.com',
  'alert@icici.bank.in',
  'customernotification@icici.bank.in',
  'alerts@hdfcbank.bank.in',
  'alerts@axis.bank.in',
];

const senderQuery = BANK_SENDERS.map(s => `from:${s}`).join(' OR ');
let messages = [];
let pageToken;

// P0-4: Loop over nextPageToken to prevent silent email loss
do {
  const { data } = await gmail.users.messages.list({
    userId: 'me',
    q: `(${senderQuery}) newer_than:30d`,
    maxResults: 100,
    pageToken,
  });
  stats.recordEvent('pagesFetched');

  if (data.messages && data.messages.length > 0) {
    messages.push(...data.messages);
    for (let i = 0; i < data.messages.length; i++) {
      stats.recordEvent('messagesDiscovered');
    }
  }
  pageToken = data.nextPageToken;
} while (pageToken);

02 MIME Tree Traversal & HTML Stripping

Gmail API returns emails as nested MIME trees (e.g. multipart/mixed wrapping multipart/alternative containing text/plain and text/html). The function extractBodies() walks this recursive tree and decodes base64url payloads:

fetchAndParse.js — MIME Tree Walker JavaScript 
function decodeBase64Url(data) {
  return Buffer.from(data, 'base64').toString('utf-8');
}

function extractBodies(payload) {
  let htmlBody = '';
  let plaintextBody = '';
  (function walk(part) {
    if (!part) return;
    if (part.mimeType === 'text/html' && part.body && part.body.data) {
      htmlBody += decodeBase64Url(part.body.data);
    } else if (part.mimeType === 'text/plain' && part.body && part.body.data) {
      plaintextBody += decodeBase64Url(part.body.data);
    }
    (part.parts || []).forEach(walk);
  })(payload);
  return { htmlBody, plaintextBody };
}

HTML Stripping & Whitespace Normalization

When an email only has an HTML part (standard for HDFC, IndusInd, and Axis), stripHtml(html) converts rich styling and layout tables into clean, regex-parseable text:

bankParsers.js — stripHtml Engine JavaScript 
function stripHtml(html) {
  return html
    .replace(/<style[^>]*>[\s\S]*?<\/style>/gi, '')   // Remove CSS stylesheets
    .replace(/<script[^>]*>[\s\S]*?<\/script>/gi, '') // Remove JavaScript
    .replace(/<[^>]+>/g, ' ')                         // Strip all HTML tags to space
    .replace(/&nbsp;/gi, ' ')                         // Normalize non-breaking spaces
    .replace(/&amp;/gi, '&')                          // Unescape XML entities
    .replace(/\s+/g, ' ')                            // Collapse runs of whitespace
    .trim();
}

04 P0-2: Non-Transactional Pre-Filter & Precedence Engine

nonTransactional.js acts as a high-speed pre-filter to drop non-transactional messages (OTPs, login notices, statement generation alerts, credit limit upgrades) before expensive regex or LLM calls.

Core P0 Safety Rule: Completed Transactions Beat Negative Text

A message that contains evidence of completed money movement (e.g. debited, spent, successfully paid) MUST NEVER be dropped merely because it also mentions a historical failure ("Previous payment failed") or a future billing notice ("Payment due next month").

nonTransactional.js — P0 Precedence Logic JavaScript 
const COMPLETED_TRANSACTION_RE =
  /\b(debited|credited|spent|paid|withdrawn|purchased|purchase of|sent|received|transferred|disbursed|successfully\s+(?:paid|debited|credited)|transaction\s+amount)\b/i;

const NON_TRANSACTIONAL_RE =
  /\b(OTP|one[- ]time password|logged in|login (has been |was )?enabled|password|verification code|pending payment request|payment request|requested you to pay|tap to pay|is pending|failed|declined|attempt.*could not be completed|cashback|is due on|due date|scheduled for auto-debit|offer|loan|avail|credit limit|limit increase|apply now|upcoming|activat(ed|ion))\b|\bbill\b.{0,60}?\b(is ready|is generated|generated)\b|\bstatement\b.{0,60}?\b(generated|is ready)\b/i;

const FUTURE_RE = /\b(will be debited|is due|due on|due date|scheduled for|will be credited)\b/i;
const FAILED_RE = /\b(failed|declined|rejected|cancelled|cancel|not debited|no amount (was|has been) debited)\b/i;
const BILL_PAYMENT_RE = /\b(received payment|payment.*received|bill payment.*received)\b/i;

function hasCompletedMoneyMovement(text) {
  // Mask out pure future and negation phrases so "will be debited" or "not debited" do not give false positives
  const withoutFutureOrNegated = text
    .replace(/\bwill\s+be\s+(?:debited|credited|paid|transferred)\b/gi, '')
    .replace(/\b(?:not|never|could\s+not\s+be|no\s+amount\s+(?:was|has\s+been))\s+(?:debited|credited|paid|transferred)\b/gi, '');

  return COMPLETED_TRANSACTION_RE.test(withoutFutureOrNegated);
}

function isNonTransactional(text) {
  if (!text) return false;

  // 1. Strong evidence of completed money movement wins over footers / administrative text
  if (hasCompletedMoneyMovement(text)) return false;

  // 2. Pure future / scheduled notifications without completed money movement
  if (FUTURE_RE.test(text)) return true;

  // 3. Pure failure / decline notifications without completed money movement
  if (FAILED_RE.test(text)) return true;

  // 4. Bill payment confirmations
  if (BILL_PAYMENT_RE.test(text)) return true;

  // 5. OTP, login, or administrative noise
  if (NON_TRANSACTIONAL_RE.test(text)) return true;

  return false;
}

05 Subject Header Extraction & Security Footers

Case Study: The Axis Bank ₹167 Transaction

Axis Bank credit card emails have security warnings in their HTML footer: "Please do not share your Internet Banking details, password or OTP with anyone... Total Credit Limit: INR 44000".

Because the body contained the keywords OTP and Credit Limit, NON_TRANSACTIONAL_RE matched. In the body, Axis formatted the charge as Transaction Amount: INR 167 while the completion verb spent was located in the Subject line (INR 167 spent on credit card no. XX9992).

By extracting the Subject header in fetchAndParse.js and prepending it to the body text (`${subject}\n${bodyText}`), and including transaction\s+amount in COMPLETED_TRANSACTION_RE, the completion gate activates cleanly.

07 LLM Fallback & Single-Store Architecture

If an email or SMS arrives from an allowlisted bank but the template does not match any regex, the pipeline falls back to OpenRouter (meta-llama/llama-3.3-70b-instruct):

The Single-Store Rule

In both server.js (SMS) and fetchAndParse.js (Email), the LLM is called before writing to the database. If the LLM succeeds, the resolved transaction is inserted directly into the matching engine. A needsReview: true placeholder is created only if the LLM API throws or is offline, and is automatically re-matched upon recovery.

08 P0-1 & P0-3: Mandatory Conflict Checks (hasConflict)

The core financial safety principle of the deduplication engine is:

"For financial data, prefer keeping two transactions over incorrectly merging two different transactions."

Before any similarity scoring or multi-level reconciliation runs, hasConflict(a, b) executes strict identity checks. If both records have known identity fields that disagree, auto-merge is hard-blocked.

matchingEngine.js — Mandatory hasConflict Gate JavaScript 
function hasConflict(a, b) {
  if (!a || !b) return false;

  // 1. Conflicting reference numbers (both present and not equal) -> NEVER MERGE
  if (a.refNo && b.refNo && a.refNo !== b.refNo) {
    return true;
  }

  // 2. Conflicting last4 or account numbers (both present and not equal) -> NEVER MERGE
  const aLast4 = lastFourOf(a);
  const bLast4 = lastFourOf(b);
  if (aLast4 && bLast4 && aLast4 !== bLast4) {
    return true;
  }

  // 3. Conflicting transaction direction / type (debit vs credit) -> NEVER MERGE
  if (a.type && b.type && a.type !== b.type) {
    return true;
  }

  // 4. Conflicting bank -> NEVER MERGE
  if (a.bank && b.bank && a.bank !== b.bank) {
    return true;
  }

  return false;
}

09 Multi-Source Deduplication Hierarchy & Anchor Gates

When an SMS and an Email arrive for the same payment, matchingEngine.js reconciles them into 1 canonical transaction using a 4-level matching hierarchy protected by identity anchors:

Level Strategy Confidence Required Conditions & Safety Gates
Level 1 Exact Reference Match 1.00 Identical refNo on both SMS and Email.
Level 1.5 Partial Reference Match 0.92 One side has refNo, other has null; same bank, amount, type, last4, ≤ 10 min window, zero conflict.
Level 2 Deterministic Structural Match 0.95 Same bank, amount, type, exact merchant (similarity === 1), ≤ 10 min window, zero conflict.
Level 3 Anchored Weighted Scoring 0.85 – 0.94 Score ≥ 0.85 AND MANDATORY STRONG IDENTITY ANCHOR (same last4 or compatible refNo). Merchant similarity alone NEVER merges.
Level 4 AI Arbitration Dynamic Ambiguous score band (0.55 – 0.85) when no hard conflict exists. Defaults to NO MERGE if AI is unsure or offline.
