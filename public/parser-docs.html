Email & SMS Ingestion Architecture

A comprehensive breakdown of headers, MIME payload extraction, HTML sanitization, non-transactional pre-filtering, and regex classification in gmail-txn-parser.

01 Gmail Ingestion, Headers & Sender Allowlist

Email ingestion runs in fetchAndParse.js via the official Google Gmail REST API (v1). Rather than querying all mail, it starts with an allowlist query to completely ignore non-banking traffic (promos, newsletter subscriptions, social notifications) before fetching payloads.

fetchAndParse.js — Allowlist Query JavaScript 
const BANK_SENDERS = [
  'transactionalert@indusind.com',
  'onlinesbicard@sbicard.com',
  'alert@icici.bank.in',
  'customernotification@icici.bank.in',
  'alerts@hdfcbank.bank.in',
  'alerts@axis.bank.in',
];

const senderQuery = BANK_SENDERS.map(s => `from:${s}`).join(' OR ');
const { data: list } = await gmail.users.messages.list({
  userId: 'me',
  q: `(${senderQuery}) newer_than:30d`,
  maxResults: 50,
});

Extracted Email Headers

For each message returned by the query, gmail.users.messages.get({ format: 'full' }) is called. The parser extracts the following specific headers:

Header Name Raw Example Transformation / Parser Use

Subject INR 167 spent on credit card no. XX9992 Prepended to the extracted body text (`${subject}\n${bodyText}`) so transaction keywords (like "spent") are available to regex and filters.

msg.internalDate 1787333591000 (Epoch ms) Converted to standard ISO-8601 UTC timestamp: new Date(Number(internalDate)).toISOString().

02 MIME Tree Traversal & HTML Stripping

Gmail API returns emails as nested MIME trees (e.g. multipart/mixed wrapping multipart/alternative containing text/plain and text/html). The function extractBodies() walks this recursive tree and decodes base64url payloads:

fetchAndParse.js — MIME Tree Walker JavaScript 
function decodeBase64Url(data) {
  return Buffer.from(data, 'base64').toString('utf-8');
}

function extractBodies(payload) {
  let htmlBody = '';
  let plaintextBody = '';
  (function walk(part) {
    if (!part) return;
    if (part.mimeType === 'text/html' && part.body && part.body.data) {
      htmlBody += decodeBase64Url(part.body.data);
    } else if (part.mimeType === 'text/plain' && part.body && part.body.data) {
      plaintextBody += decodeBase64Url(part.body.data);
    }
    (part.parts || []).forEach(walk);
  })(payload);
  return { htmlBody, plaintextBody };
}

HTML Stripping & Whitespace Normalization

When an email only has an HTML part (standard for HDFC and IndusInd), stripHtml(html) converts rich styling and layout tables into clean, regex-parseable text:

bankParsers.js — stripHtml Engine JavaScript 
function stripHtml(html) {
  return html
    .replace(/<style[^>]*>[\s\S]*?<\/style>/gi, '')   // Remove CSS stylesheets
    .replace(/<script[^>]*>[\s\S]*?<\/script>/gi, '') // Remove JavaScript
    .replace(/<[^>]+>/g, ' ')                         // Strip all HTML tags to space
    .replace(/&nbsp;/gi, ' ')                         // Normalize non-breaking spaces
    .replace(/&amp;/gi, '&')                          // Unescape XML entities
    .replace(/\s+/g, ' ')                            // Collapse runs of whitespace
    .trim();
}

03 SMS Webhook Ingestion & Normalization

SMS transaction alerts from banks are pushed via an iOS Shortcuts automation running on the user's phone directly to POST /api/sms-ingest on the server.

Field Source from iOS Shortcut Server Normalization in server.js
Sender body.sender (e.g. HDFCBK-S, ICICIB-T) Matched against SMS regex allowlists (ICICI, HDFC, SBI, Axis, OneCard, Axio).
Date / Time body.date (e.g. 21/08/2026, 22:23) Processed via safeIsoDate() to support Indian DD/MM/YYYY and 12-hour AM/PM formats into strict ISO-8601 UTC.
Message ID Calculated Deterministically crypto.createHash('sha1').update(`${sender}|${text}|${isoDate}`).digest('hex')

04 How nonTransactional.js Works

Banks send many messages from their primary notification sender that are not actual transactions (e.g. OTPs, login notices, statement generation alerts, credit limit upgrades). nonTransactional.js acts as a high-speed pre-filter to drop this noise before expensive regex or LLM calls.

nonTransactional.js — Complete Logic JavaScript 
const NON_TRANSACTIONAL_RE =
  /\b(OTP|one[- ]time password|logged in|login (has been |was )?enabled|password|verification code|pending payment request|payment request|requested you to pay|tap to pay|is pending|failed|declined|attempt.*could not be completed|cashback|is due on|due date|scheduled for auto-debit|offer|loan|avail|credit limit|limit increase|apply now|upcoming|activat(ed|ion))\b|\bbill\b.{0,60}?\b(is ready|is generated|generated)\b|\bstatement\b.{0,60}?\b(generated|is ready)\b/i;

const COMPLETION_VERB_RE =
  /\b(debited|credited|spent|paid|withdrawn|purchase[d]?|sent|received|transferred|disbursed|transaction\s+amount)\b/i;

const FUTURE_RE = /\b(will be debited|is due|due on|due date|scheduled for|will be credited)\b/i;
const FAILED_RE = /\b(failed|declined|rejected|cancelled|cancel|not debited|no amount (was|has been) debited)\b/i;
const BILL_PAYMENT_RE = /\b(received payment|payment.*received|bill payment.*received)\b/i;

function isNonTransactional(text) {
  if (!text) return false;
  if (FUTURE_RE.test(text) || FAILED_RE.test(text) || BILL_PAYMENT_RE.test(text)) return true;
  return NON_TRANSACTIONAL_RE.test(text) && !COMPLETION_VERB_RE.test(text);
}

Pre-Filter Decision Truth Table

Condition Example Message isNonTransactional Outcome
FUTURE_RE.test() === true "Rs. 499 will be debited on 25/08 for Netflix" TRUE Dropped (Future obligation, no money moved yet)
FAILED_RE.test() === true "Transaction for Rs. 399 at Epic Games is Declined" TRUE Dropped / Excluded from unsplit ledger
NON_TRANSACTIONAL_RE === true && COMPLETION_VERB_RE === false "OTP for ICICI Bank login is 123456. Do not share." TRUE Dropped (Administrative / Security OTP)
NON_TRANSACTIONAL_RE === true && COMPLETION_VERB_RE === true "INR 167 spent on card XX9992 ... Security Note: Do not share OTP" FALSE PASSED TO PARSER (Completion verb overrides footer noise)
Standard Spend Message "Spent Rs.316 On HDFC Bank Card 6558 At SWIGGY FOOD" FALSE PASSED TO PARSER

05 The Security Footer vs. Completion Verb Override

Case Study: The Axis Bank ₹167 Transaction

Axis Bank credit card emails have security warnings in their HTML footer: "Please do not share your Internet Banking details, password or OTP with anyone... Total Credit Limit: INR 44000".

Because the body contained the keywords OTP and Credit Limit, NON_TRANSACTIONAL_RE matched. In the body, Axis formatted the charge as Transaction Amount: INR 167 while the word spent was in the Subject line (INR 167 spent on credit card no. XX9992).

By extracting the Subject and adding transaction\s+amount to COMPLETION_VERB_RE, the completion gate activates and overrides the footer noise.

07 LLM Fallback & needsReview Safety Net

If an email or SMS arrives from an allowlisted bank but the template does not match any regex (e.g. bank updated their phrasing), the pipeline falls back to OpenRouter (meta-llama/llama-3.3-70b-instruct) with a strict financial prompt:

llmFallback.js — System Prompt Text 
You are a strict transaction classifier and extractor.
First determine whether this message represents an actual financial transaction.
The presence of a monetary amount is NOT evidence of a transaction.
Loan offers, credit offers, advertisements, cashback, bill reminders, future scheduled payments, OTPs must be classified as NON_TRANSACTION.
If there is insufficient evidence, output ONLY: {"notATransaction": true}
If valid: output ONLY JSON: { "bank", "instrument", "last4", "amount", "currency", "merchant", "type", "status", "rawDate", "refNo" }
The Single-Store Rule

In both server.js (SMS) and fetchAndParse.js (Email), the LLM is called before writing to the database. If the LLM succeeds, the resolved transaction is inserted directly into the matching engine. A needsReview: true placeholder is created only if the LLM API throws or is offline.

08 Multi-Source Deduplication (Matching Engine)

When an SMS and an Email arrive for the same payment, matchingEngine.js reconciles them into 1 canonical transaction using a 4-level matching hierarchy:

Level Strategy Confidence Conditions
Level 1 Exact Reference Match 1.00 Identical refNo on both SMS and Email.
Level 1.5 Partial Ref Match 0.92 Matching bank, amount, last4 within a 10-minute window.
Level 2 Deterministic Tight Window 0.95 Same bank, amount, debit/credit type, exact merchant name, ≤ 10 min window.
Level 3 Weighted Similarity Scoring 0.85 – 0.94 Merchant Similarity (50%) + Last4 Match (25%) + Time Proximity (25%).
Level 4 AI Arbitration Dynamic Fires only for ambiguous score band (0.55 – 0.85). Prefer false when unsure.
